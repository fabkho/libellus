## #131 phase 0 — can a PWA reach the member's ebook files on Android? (spike result)

**Short answer:** yes, Chrome on Android (132+) gives a PWA a real folder handle and it can list and read EPUBs in place. But the folder permission **does not survive** a restart of the app: every cold start, every page reload and every kill by Android needs a user tap to re-allow it. It is not rare, so I recommend **copying each linked EPUB into OPFS** (reading never needs a permission) and using the folder handle only for **discovery**. Details, numbers and risks below.

Evidence: branch [`spike/ebook-files`](https://github.com/fabkho/libellus/tree/spike/ebook-files/spikes/ebook-files) (`spikes/ebook-files/`: the test PWA, scripts, 22 screenshots ≤ 1000 px, raw event logs). No PR, nothing merges. Test files: 5 Project Gutenberg EPUBs (public domain, 0.6–1.8 MB) + two big ones (7.6 MB, 23.7 MB) for timing.

**Setup.** Android emulator (Pixel 9 AVD, API 37 / Android 17, Google Play image), Chrome 145.0.7632.218, the spike page served from the Mac over `adb reverse` as `http://localhost:3126` (a secure context), once as a normal Chrome tab and once "installed" (⋮ → Add to Home screen → Install). Desktop: Chrome for Testing 153, headless (see the limits).

### What the emulator cannot show (read first)
1. **No WebAPK.** Without a Google account the install is a Chrome "webapp" shortcut (Chrome badge on the icon; same as docs/TESTING.md says for #91). It runs standalone (`display-mode: standalone`) and uses the same storage, but Chrome's **share sheet entry and `persist()` behaviour of a real WebAPK could not be tested**. Share-target results below come from the *same multipart POST* the share sheet makes, fed by the Android file picker, not from a Files-app share intent. **One manual check on the owner's phone is still needed** (HTTPS preview, share 1 and 3 EPUBs from Files/Downloads).
2. **Desktop Chrome:** automation cannot drive the native folder dialog here (no display for `osascript`/`screencapture`), so the desktop run used an OPFS directory handle as stand-in for the same scan/read/metadata code; permission behaviour on desktop comes from Chrome's docs.
3. The emulator is software-rendered and shares the Mac's CPU: timings are indicative, not phone numbers.

Every slice read costs ~30 ms of Android file-system round trip, so on a content URI one big read beats five small ones up to ~25 MB; both are fast enough for a worker. Desktop (OPFS stand-in): 1–5 ms for any of them, 50-file scan 1–6 ms.

### Recommendation for phase 1: **copy into OPFS; the folder handle is for discovery only**
- **Reading in place fails the owner's own test** ("prefer in place if the prompt is rare"): the prompt is *not* rare. It returns on every cold start, every reload and every time Android reclaims the app, and *Read now* is the primary action, so it would sit behind a permission tap each session (and offline, with the folder gone, it would not work).
- Copy is cheap here: ~25–70 ms and 0.6–25 MB per book; quota is GBs. After the copy, **Read now needs no permission, works offline, and is instant**.
- One storage path for all three sources: share target and `<input type=file>` hand over a one-shot `File` with **no reference to the original**, so they must be copied anyway. Folder mode then only adds "find new files".
- Store the original `size`/`lastModified` of folder files (the share target loses `lastModified`) plus the first-MB hash to recognise a file again, as the spec says.
- Request `navigator.storage.persist()` after the first link (false in the emulator; a real installed app may get it). If OPFS is evicted anyway, the link shows as *missing* and is rebuilt from folder/share, as in the spec.

### UX implication (exact)
- **Folder mode:** setup = pick folder (3 system steps, once ever). Afterwards **per app session: tap "Scan" → Chrome's "Allow this site to view and copy files?" → Allow = 2 taps**, then the scan runs (names first ≈ 0.3 s for 50 files; new files copied and matched). Libellus **cannot** prompt on its own: `requestPermission()` needs a gesture, so "scan on app open only if already granted" is true in practice only after the member has tapped Scan in that session. No silent background rescans after a restart.
- **Share target / Add ebook:** 0 permission taps (share sheet or picker), file arrives and is linked immediately.
- **Read now / progress:** 0 taps, offline.
- Copy: *"Choose a subfolder such as Download/Books. Android does not allow the Download folder itself."* — needed in the folder step, because browsers save to the root.

### Risks / open points
1. **Emulator limits** (above): real share-sheet registration, `persist()` and any persistent-permission behaviour of a **real WebAPK** are untested; one phone check with an HTTPS preview before phase 1 ships. If a WebAPK did grant persistence, in-place could be revisited, but the copy design stays correct for share/picker anyway.
2. **Download root is not selectable** → folder mode fits members who keep books in a subfolder; everyone else uses the share target. Phase 1 copy must say this.
3. **A page reload drops the permission** in the installed window; the app's `registerType: 'autoUpdate'` reloads on a new build, so avoid reloading while a scan is waiting, and never assume `granted` across navigations.
4. **share_target change:** POST + multipart is required for files (one `share_target` per manifest). The SW must handle POST `/share` (and a Pages Function fallback for a missing SW); keep #91's GET behaviour by redirecting text-only POSTs. `sw-sync.js` shows the existing `importScripts` pattern; the share code would be a second imported script.
5. **ISBN matching:** public-domain EPUBs have no ISBN (Gutenberg: URL ids); purchased/other EPUBs often do. Untested on real ISBN OPFs, so fuzzy title+author needs to be good.
6. **Storage eviction** without `persist()`; mitigated by *missing → re-link*.
7. **Chrome-only folder mode:** no Safari/Firefox support; iOS is input-picker only (no share target either), so iOS members copy via the picker.
8. Timings are from an emulator; SAF round-trip per call (~12 ms `getFile`, ~30 ms per slice) may differ on a phone. E2e for the picker must mock it (a synthesised gesture cannot open it; real touch via `adb input tap` can).
