# Parity checklist — the behavioural reference

The **web app is the reference** (SPEC.md). This file, together with the Playwright flows in
`web/e2e/`, is what any native port is built and checked against. Every PR that adds or changes a
screen updates its entry here — describe behaviour, not Vue code, so a port does not have to read
`.vue` files to know what a screen does.

Rules for a port, if one happens:
- Match the web behaviour exactly. No extra features, no redesign. Native idioms are allowed where the
  platform demands them (navigation stack, sheets, haptics), and noted in the entry.
- Same names across platforms: `app/data/` repositories, stores ↔ ViewModels
  (`useLibraryStore` ↔ `LibraryViewModel`).
- IDs: the web `data-testid` is the native `accessibilityIdentifier` (`<screen>.<element>`).
- Copy: the keys in `web/i18n/locales/en.json` are the keys of the native string catalogues
  (`Localizable.strings`, `strings.xml`). Entries name keys, not sentences.
- An entry is done on a platform only when its flow passes there (Playwright on web, Maestro native).


## Screens

### Sign in  (web: `app/pages/sign-in.vue`)
Purpose: the way back in for a member; one field, the address.
Layout: the way-in frame (`components/auth/Frame.vue`, docs/DESIGN.md): a wall of cloth covers behind a veil, the wordmark and tagline, the screen's eyebrow title, the form, the link to the other screen at the bottom. Same frame on Sign up and Verify, in both themes; the theme is the device's or the one chosen in the Profile (see Theme).
States: form · busy (submit disabled) · error (inline under the field, the field's rule turns red) · config problem (the build has no Supabase URL/key; replaces the form)
Actions → result:
- Submit address → asks Supabase Auth for a six-digit code for that address **without creating an account** (`createAuth.requestCode`). Known address: the address is stored as the *pending sign-in* (see Verify) and the app goes to Verify. Unknown address: not an error, the app goes to Sign up with the address prefilled.
- "Sign up" link (`signIn.signUpLink`) → Sign up (address field empty).
Edge cases: a malformed address is refused by the field (browser validation) or by the backend (`email_invalid`); asking for another mail within a second is `rate_limited`. A signed-in member opening this screen is sent to Home. A signed-out launch with a pending address is sent to Verify instead.

IDs: `signIn.brand`, `signIn.title`, `signIn.email`, `signIn.error`, `signIn.submit`, `signIn.signUp`, `signIn.configProblem`
Flow: `web/e2e/auth.spec.ts` (every flow starts here)

### Sign up  (web: `app/pages/sign-up.vue`)
Purpose: a new member joins with their address and an invite code. Libellus is invite-only.
Layout: the way-in frame (see Sign in).
States: form · busy · error under the invite field (`invite_*`) or under the address field (anything else)
Actions → result:
- Submit address + invite code → the invite is pre-flighted (`invite_code_status` answers valid / invalid / expired / exhausted / missing), then Supabase Auth creates the account and mails a six-digit code (`createAuth.requestSignUpCode`); the address is stored as the pending sign-in and the app goes to Verify. Nothing is spent yet.
- "Sign in" link → Sign in.
Edge cases: the database gate is authoritative (a trigger on account creation refuses a missing, unknown, expired or used-up code); the pre-flight only tells the form why. The invite is **consumed when the address is proved** (Verify), and judged again under a lock: if the last use went to someone else in between, Verify fails with `invite_gone`. Codes are case-insensitive and trimmed. Signing up with an address that already has an account just mails it a sign-in code and costs no invite. Addresses that never get proved are removed after a day.
Copy keys: `app.name`, `app.tagline`, `signUp.title`, `signUp.intro`, `signUp.emailLabel`, `signUp.emailPlaceholder`, `signUp.inviteLabel`, `signUp.invitePlaceholder`, `signUp.submit`, `signUp.hasAccount`, `signUp.signInLink`, `auth.error.invite_required|invite_invalid|invite_expired|invite_exhausted`
IDs: `signUp.brand`, `signUp.title`, `signUp.email`, `signUp.emailError`, `signUp.inviteCode`, `signUp.inviteError`, `signUp.submit`, `signUp.signIn`
Flow: `web/e2e/auth.spec.ts` (sign up with the dev invite; an invalid invite is refused under its field)
- [x] Web  - [ ] iOS  - [ ] Android

### Verify  (web: `app/pages/verify.vue`)
Purpose: type the six-digit code from the mail. Typed, never a link, so it works inside the installed iOS PWA.
Layout: the way-in frame (see Sign in); six drawn cells, the next one lit with the lamp caret; Resend is a quiet pill, "Use another email" the link at the bottom.
States: waiting for the code · busy · error (under the code, all cells red) · resend cooling down (60 s after each mail; the pill is dimmed and counts down)
Actions → result:
- Type the sixth digit → submits (no button). Success: the member is signed in, the pending address is dropped, the app goes to Home. Failure: the error shows, the field clears and keeps the keyboard.
- Resend → mails a new code to the pending address (the sign-in call, in both flows) and restarts the 60 s cooldown.
- "Use another email" → drops the pending address, goes to Sign in.
Edge cases: **the pending address is persisted for one hour** (`libellus.pendingSignIn` in local storage: address, flow, time sent), so iOS killing the installed app while the member reads Mail does not lose it: a signed-out launch with a pending address opens Verify, and Verify without one goes to Sign in. After an hour it is discarded (the code expired too). One input, not six: the cells are only a drawing, so the iOS code suggestion and paste work (`autocomplete="one-time-code"`, numeric keyboard, digits only). A wrong, expired or already-used code is one error (`code_invalid`): Supabase deliberately cannot tell them apart. `invite_gone` when the invite ran out between Sign up and now. `rate_limited` when resend is tapped twice.
Copy keys: `app.name`, `app.tagline`, `verify.title`, `verify.sentTo`, `verify.codeLabel`, `verify.resend`, `verify.resendIn`, `verify.changeEmail`, `auth.error.code_invalid|invite_gone|rate_limited|unknown`
IDs: `verify.brand`, `verify.title`, `verify.sentTo`, `verify.code`, `verify.error`, `verify.resend`, `verify.changeEmail`
Flow: `web/e2e/auth.spec.ts` (the code read from Mailpit; a mistyped code; the pending address survives a relaunch)
- [x] Web  - [ ] iOS  - [ ] Android

### Tab shell  (web: `app/layouts/tabs.vue`, `components/shell/*`; pages `app/pages/{index,library}.vue`)
Purpose: the signed-in frame: each tab's header with the avatar, the page, the floating tab bar, and the search overlay that opens over all of it. Home is described in its own section below. A pushed screen (the book page) lives in the same frame without the header (see Book).
Layout: a page header on top (`shell.header`, iOS's Large Title bar: under the safe area a 44 pt row with only the avatar at the right, then 10 below it the title — the date eyebrow over the greeting on Home, the large title on Library — and 10 under that the page), the page, and over the page's bottom edge the floating tab bar (`shell.tabs`: Home, Library, Search as a capsule). The search overlay replaces the tab bar with the palette (see Search); the avatar opens the Profile (see Profile). Wide screens: the same column, centred.
States: content (each tab shows its empty state) · search overlay closed / open (keyboard up: "typing", or down)
Actions → result:
- Tap Home or Library in the tab bar → shows Home (`/`) or Library (`/library`), scrolled to where that tab was left (from the tab bar, the search palette's tabs or any link; a tab never left, or entered after signing in again, opens at its top). Back and forward return to the place the browser saved for that entry. A place deeper than the page is tall when the router scrolls (a slow device, the content still coming in) is landed on as soon as the page has grown to it, for at most 2 s (`PLACE_PATIENCE`; then as far down as the page goes), and not at all once the member scrolls, taps or types herself meanwhile (`untilReachable` in `utils/tabPlaces.ts`); until the page is in its place the document carries `data-moving`. The current tab is full ink with a lamp dot and its `aria-current="page"`; the others are faint. The header shows the page's title: Home under a date eyebrow (`home.today`, e.g. "Friday · 2 Oct"), Library large on its own.
- Tap the tab already showing → it scrolls back to its top (smoothly; at once with Reduce Motion); nothing navigates. Native: each tab's own navigation stack keeps its place.
- Tap Search in the tab bar, or the search prompt in an empty state → the **search overlay** opens over the current page; **the URL does not change** and the page stays behind it, blurred and veiled. The query field has the keyboard ("typing"): the bottom row is the search icon, the field (placeholder `search.placeholder`), a clear button once something is typed, and **Cancel**. With the keyboard down the row shows Home and Library at its left (the current one lit) instead of Cancel; tapping one goes there and closes the overlay. Above the row are the results (see Search).
- Close the overlay → Cancel (while typing), a tap on the page behind it (`search.backdrop`), swiping the palette down (more than 80 px, or a quick flick), Escape, or going to another page (the palette turns back into the capsule, whose Home and Library return only once the flying Search icon has passed them) (a navigation that started while it was open; a tab tapped just before Search whose page is still loading arrives behind the open search instead of closing it). The query is dropped; the page underneath is as it was.
- Tap the avatar (the initials of her name when she gave one: "Fabian" → `F`, "Ida Tester" → `IT`; otherwise of the address: `ida.tester@example.com` → `IT`, `ida@example.com` → `ID`) → opens the **Profile** (`/profile`, a pushed screen; see Profile), which holds the account: the address, **Name** (see Member name), the **Dark mode** switch, **Import books**, **Sign out**. (Until #78 these lived in a small avatar menu.)
- Dark mode switch (in the Profile) → see Theme below. On when dark is showing.
- Scroll any page of the shell → once something has scrolled under the status bar, a thin veil of the surface colour (`shell.scrollEdge`: solid over the top inset, fading out `ms` (12) below it, no blur, not under a pushed screen's top bar; in a browser tab, where the inset is 0, only the 12 px fade) keeps what runs under the clock from crowding it; at the top of the page it is not there, so a book's light shows. It never takes a tap. Native: the platform's own scroll edge effect.
- Sign out (in the Profile) → ends the session on the device and revokes it on the server, removes everything the device cached under the `libellus.` prefix (the pending address, the device's copy of the Library: see Offline and install), goes to Sign in. The theme preference is not under that prefix and stays.
Every navigation is said: a polite live region reads the new document title (`NuxtRouteAnnouncer` in `app.vue`; a native port moves its screen reader's focus to the new screen). Edge cases: the session is restored on launch before the first route resolves, so a signed-in member never sees Sign in flash past. Signed-out members opening any route are sent to Sign in (to Verify if a code is pending); signed-in members opening Sign in / Sign up / Verify are sent Home. A session that ends elsewhere (another tab, a failed refresh) lands on Sign in too. In dev builds, routes starting with `/prototype` skip the guard. There is no `/search` route any more (search is never a page; nothing deep-links to it yet): it is an unknown route like any other. Wide screens: the same layout in a centred column with hairlines left and right; the tab bar and the overlay stay centred. Header, tab bar and overlay respect the device's edges (Device edges, below); with the keyboard up the overlay sits right above it. Native: the overlay is a sheet-like panel over the current view, not a pushed screen. Web on iOS: a passive no-op `touchstart` listener on the document lets Safari apply the press styles (`:active`).
Copy keys: `app.name`, `tabs.home|library|search`, `home.greeting.*|today|emptyTitle|empty`, `library.title|emptyTitle|empty`, `search.title|placeholder|close|clear|empty`, `common.cancel`, `shell.tabsLabel`, `shell.avatarLabel` (the account's copy is the Profile's, see Profile)
IDs: `shell.header`, `shell.avatar`, `profile.email`, `profile.name`, `profile.nameValue`, `profile.theme`, `profile.signOut`, `shell.tabs`, `shell.tab.home|library|search`, `home.date`, `home.title` (the greeting), `home.emptyTitle`, `home.empty`, `home.search`, `library.title`, `library.emptyTitle`, `library.empty`, `library.search`, `search.overlay`, `search.backdrop`, `search.query`, `search.clear`, `search.cancel`, `search.tab.home|library`, `search.empty`
Flow: `web/e2e/tabs.spec.ts` (each tab opens where it was left, the current tab tapped again goes to its top, back returns to the saved place; each place read once the page is in it), `web/tests/tab-places.test.ts` (the places, and the wait for a page tall enough), `web/e2e/auth.spec.ts` (sign up → Home → Library → a reload keeps the session → the Search tab opens the overlay over Library and Cancel closes it → avatar → the Profile's Sign out → signed out again; the overlay closes on the page behind, a swipe down and Escape; the theme test below) and `web/e2e/search.spec.ts` (the tab bar turns into the palette and back by Cancel, the page behind, Escape and a swipe down — a short one settles back open — the morph turned around halfway either way, and the palette sitting `--spacing-sm` above a keyboard of any height, following it, and starting the next opening unlifted, with a stand-in visual viewport; end states only; `web/tests/keyboard.test.ts` for the geometry)

### Theme  (web: `app/utils/theme.ts`, `app/stores/theme.ts`, the switch in `components/profile/Account.vue`)
Purpose: light (D's Day) or dark (D's Night). Follows the phone until the member chooses (issue #1, story 70).
Layout: one switch row (`role=switch`), `profile.account.theme`, in the Profile's account rows between Name and Import books; nothing else on screen changes except the colours.
States: no preference (follows the device, live) · light · dark. The switch shows two states only: on = dark is showing.
Actions → result:
- First tap on the switch → stores **the opposite of what is showing**: on a dark phone with no preference, Light. Every later tap flips between Light and Dark. There is no way back to "follow the phone" from the interface.
- The stored choice → `<html data-theme>`, both `theme-color` tags (browser chrome, installed app's status bar) take the theme's surface colour; with no choice there is no attribute and each `theme-color` tag answers its own `prefers-color-scheme`.
Edge cases: stored on the device in local storage (`libellus-theme`), never in Supabase, not cleared by sign-out, so the way in looks as the member left it. Applied before the first paint by an inline script at the top of the HTML, so a launch never flashes the other theme. Unreadable or unknown stored values count as no preference; storage that refuses writes still flips the theme for the visit. Native: the same preference in the platform's user defaults, applied as the window's interface style; `null` = unspecified.
Copy keys: `profile.account.theme`
IDs: `profile.theme`
Flow: `web/e2e/auth.spec.ts` (a dark phone → avatar → the Profile's switch: first tap stores Light → later taps flip regardless of the phone → kept across a reload, a tab change and sign-out); the rule in `web/tests/theme.test.ts`

Layout: the Profile's **Name** row (`account.name`, pencil icon) with the name at the right, or `account.nameNone` ("Add") in the ghost colour. It opens the sheet `accountName` (`UiSheet`, title `account.nameTitle`, **Save** at the top right): one field `account.nameLabel` (placeholder `account.namePlaceholder`, at most 40 characters, autocomplete `given-name`), the hint `account.nameHint`, and, while she has a name, **Remove name** (`account.clear`).

### Profile photo  (web: `components/profile/Photo.vue` in `app/pages/profile/index.vue`, the Photo row of `components/profile/Account.vue`, the ring of `components/profile/Hero.vue`, `components/ui/Avatar.vue` in `components/shell/Header.vue`, `stores/avatar.ts`, `data/avatar.ts`, `utils/avatarRaster.ts`, `utils/crop.ts`, `composables/useCrop.ts`, the `avatars` store under `data/localData.ts`; database: `supabase/migrations/20261009120000_avatars.sql` — the bucket `avatars`, its policies, `accounts.avatar_path|avatar_updated_at`, `set_avatar`, `delete_my_account`)
Purpose: the member's own photo in her avatars instead of her initials (issue #156). Shown to her alone.
Layout: the Profile's **Photo** row (`photo.row`, camera icon) first in the account rows, with her small photo at the right or `photo.rowNone` ("Add"); the hero's ring is a button for the same (`photo.avatarLabel`). The sheet `photo` (`UiSheet`) in two states. **Her photo** (title `photo.title`): the photo in the hero's ring, `photo.private` ("Only you see it. …"), **Choose another** (`photo.replace`; without a photo `photo.choose`, primary) and **Remove photo** (`photo.remove`, danger). **The crop** (title `photo.cropTitle`, "Move and scale", **Save** at the top right): the picked picture in a square under a round mask, − / slider / + for the zoom (1× to 4×), the hint `photo.hint`. Every avatar (`UiAvatar` in each tab's header, the hero, the row) draws the photo over the initials in the same ring.
States: no photo (initials, "Add") · a photo · the crop · saving (`photo.saving`, Save disabled) · removing (`photo.removing`) · error under the content (`photo.error.unreadable|offline|too_large|not_signed_in|missing|unknown`; the sheet stays) · offline (the row is disabled and says "Offline", the hero's ring is disabled, the sheet's actions say "Offline") · saved / removed (said once in a polite status, `photo.saved|removed`).
Actions → result:
- Tap the row or the hero's ring without a photo → the device's picker opens in the same tap (`<input type="file" accept="image/*">`: images only; phones offer the camera and the library). With a photo → the sheet with it; Choose another opens the picker.
- A picture is picked → decoded upright (the browser applies the EXIF orientation) → the crop at 1×, the largest square in the middle. A file that cannot be decoded (`unreadable`) → the sheet with the error, nothing sent.
- Drag (one finger, the mouse) moves the picture; two fingers pinch; the wheel, the slider, − and + zoom around the square's centre; the square is focusable (`photo.area`, a labelled group described by the hint): arrows move it (Shift: four times as far), + and − zoom. The picture always covers the square (`utils/crop.ts`: `clampPan`, `zoomAround`, `cropRect`).
- Save → on the device: the square cut out of the original in a canvas, scaled down in halves to **512 px** and **128 px** (never upscaled: a smaller cut-out keeps its own size), encoded as **WebP** (JPEG for both where the browser cannot encode WebP: Safari), the quality stepped down from 0.86 until each file is ≤ 100 kB, and every metadata segment (EXIF with GPS, XMP, ICC, IPTC, comments) stripped (`encodeAvatar`, `stripMetadata`). Then **two uploads and one call**: `avatars/<her id>/<hash>.webp` and `<hash>-128.webp` (hash: the first 32 hex digits of the large file's SHA-256), then `set_avatar(path)`, which checks the path's shape and that both files are there, sets `accounts.avatar_path` and `avatar_updated_at`, and returns the path before; then the rest of her folder (the old photo, anything a broken upload left) is deleted through the Storage API. The sheet closes and every avatar shows the new photo.
- Remove photo → `set_avatar(null)`, then her folder is emptied; the initials are back everywhere.
- Cancel, the scrim, Escape, a swipe down (outside the square) or Back → nothing changes.
- Opening the app → each avatar shows the photo the device keeps (IndexedDB, `libellus` database, store `avatars`: the path and both files), offline too; online, `accounts.avatar_path` is read once per sign-in and the files downloaded with her session only when the path is a new one. A path whose files are gone (a restored backup has no Storage) shows the initials.
Edge cases: the bucket is **private** (no public URL; 256 kB a file, WebP and JPEG only): she reads, lists, writes and deletes her own folder only, with the path's shape `<her id>/<32 hex>[-128].webp|jpg`; another member and a signed-out caller can do none of that (`supabase/tests/avatars_test.sql`). Signing out deletes the device's copy with the rest. Deleting the account empties her folder first (Storage files only go through the Storage API) and `delete_my_account` refuses (`photo_remains`) while a file is left. Not in the nightly database backup (docs/OPERATIONS.md, Backups).
Copy keys: `photo.*`, `common.offline`, `common.cancel`
IDs: `profile.photo`, `profile.photoValue`, `profile.avatar`, `profile.avatarPhoto`, `photo`, `photo.cancel`, `photo.action`, `photo.scrim`, `photo.sheetTitle`, `photo.file`, `photo.status`, `photo.preview`, `photo.choose`, `photo.remove`, `photo.area`, `photo.picture`, `photo.zoom`, `photo.zoomIn`, `photo.zoomOut`, `photo.error`; `data-avatar-photo` on an avatar's photo
Flow: `web/e2e/avatar.spec.ts` (Chromium: Add → the picker → the crop placed with the keys and the zoom buttons → Save → the hero, the row and the header show it; the stored file a 512 px WebP ≤ 100 kB without EXIF; a reload with the backend out of reach still shows it → the hero's ring → Choose another → only the new pair left → Remove → initials, an empty folder; an unreadable file refused); the crop and the sheet scanned in `web/e2e/a11y.spec.ts` (WebKit: the JPEG path); the geometry, the pipeline and the repository in `web/tests/avatar.test.ts`; the bucket and its policies in `supabase/tests/avatars_test.sql`
Native: the same bucket, paths, sizes and `set_avatar` through the platform's Supabase client; the platform's photo picker and its own crop; encode with the platform's image API (it writes no EXIF when given only pixels) and keep the files in the app's own storage.

### Sheets and confirmations  (web: `components/ui/Sheet.vue`, `components/ui/Confirm.vue`, `composables/useModalLayer.ts`, `composables/useBackDismiss.ts`, `composables/useKeyboardInset.ts`, `utils/keyboard.ts`)
Purpose: what every bottom sheet and every confirmation does to the rest of the app, as on iOS (issue #49, audit items 11–14).
Behaviour:
- **Out of reach behind it.** While a sheet or a confirmation is open every other part of the app is `inert` (the page, the tab bar, the search palette, a sheet under a confirmation): no tap, no Tab, no VoiceOver reaches it. The page does not scroll under it (the root's `overflow` is hidden, the sheet's own list does not hand its scroll on to the page, a drag on the scrim does nothing). Closing the top one gives the one under it back (a confirmation over the read's edit sheet → the sheet again; the page stays shut until the sheet closes too).
- **Focus.** It moves into the sheet as it opens (to the panel, or to the field a sheet marks to have the keyboard at once: the Collection name, the member name; focused in the opening tap itself, so iOS raises the keyboard with the sheet). It goes back to what opened it when it closes, if that is still there and focus was still in the sheet; a sheet that opened another (Update progress → Finish) hands its opener on.
- **The keyboard (Android).** Chrome resizes the page to what the keyboard leaves (`interactive-widget=resizes-content` in the viewport meta, `nuxt.config.ts`), as an Android app's window resizes: the sheet and the search palette stand on the keyboard by themselves (the palette `floatAbove` over it), a sheet's height shrinks with `100dvh` so its header stays in view, and the keyboard inset reads 0, so nothing is lifted twice. Without it Chrome laid the keyboard over the page and panned the page up to the focused field, which pushed the Finish sheet's header off the top.
- **The keyboard (iOS).** With the keyboard up the sheet rides on it (`translateY` by the keyboard's height less the home-indicator padding, on the keyboard curve: `keyboardInsetOf` against the layout viewport, the larger of `innerHeight` and the root's `clientHeight`: `layoutHeightOf`; `sheetLift`), its height shrinks so its top stays on screen, and the focused field scrolls into view inside the sheet (`revealDelta`, the `md` margin). The same keyboard height the search palette follows (`useKeyboardInset`; the palette sits `--spacing-sm` above it, `paletteLift`).
- **Back (#62).** The system Back — Android's back gesture and button, the browser's Back, iOS's edge swipe in a Safari tab — closes the top-most open layer and stays on the page: a confirmation before the sheet under it, then the sheet; the search the same way. Back again leaves the page. Each open layer has a history entry of its own over the page's (same address); closing it any other way (Cancel, the scrim, a swipe, Escape, the action) takes the entry off again, so no Back is spent on something already gone, and one sheet handing over to another (Update progress → Finish) keeps the one entry. A confirmation that is running its action does not close (its entry goes back). Actions → result:
- Type → after a 220 ms pause, and only from 2 characters, the query goes out to **three sources at once** (`createSearch().search`): the own Catalogue (`search_books`: the beginnings of the words of title and authors, accents and case ignored, `ß` as `ss`; the member's own Manual books included, other members' never), Apple Books (iTunes Search API, ebooks, 20 per storefront, two storefronts) and OpenLibrary (`search.json` with a reduced field list and the device language, 20 works, each as its best edition). Every answer is merged into the list as it arrives. Every new keystroke aborts the query in flight in every source; an answer only lands for the query it was asked for, so an outdated answer never overwrites a newer one. Clearing or shortening the query below 2 characters goes back to idle.
- An ISBN (10 or 13 digits, hyphens and spaces allowed, ISBN-10 converted) is looked up as an ISBN in every source (Catalogue by `isbn13`, Apple `lookup?isbn=`, OpenLibrary `search.json?isbn=`) instead of searched as text.
- Merging (`data/merge.ts`, `mergeResults`): Catalogue hits first, then Apple, then OpenLibrary, each in its own order. **The same edition** (Catalogue id, ISBN-13 with ISBN-10s converted, Apple track id, OpenLibrary edition key) is kept once; the first keeps its place and the later one fills its empty fields. **The same book** (normalised title + normalised first author: accents, case and punctuation ignored) is kept once too — one row per book, not per edition (owner decision on #12): the row shows the edition the member has, else the Catalogue's, else the first one found with a cover on Apple's CDN, else the first with any cover, else the first one found (the device language's storefront answers first; #63: a row without a cover is a Placeholder, and Apple's CDN answers in one round trip where OpenLibrary's takes up to three). A specific edition is one ISBN search away (`search.hint`).
- Ranking: by how well the query matches (`matchQuality`, 0–100): title = query (100) › title without its subtitle = query (92) › title and first-author words together, e.g. "piranesi clarke" (88) › first author = query (85) › title begins with the query (80, or 75 mid-word) › every word begins a word of the first author (70) › of the title (65) › of title and authors together (55) › of a later author only (45) › some words (up to 40). Ties: a book shown with a cover before one shown as a Placeholder (#63; mostly self-published papers OpenLibrary has no image of), then the Catalogue's, then popularity (Apple's rating count, OpenLibrary's reading-log and rating counts), then the order the sources gave. So "Piranesi" puts Susanna Clarke's novel next to the query and Gibbon's histories (Piranesi a later author) after every title match. **The match quality is then adjusted** (`rankScore`, #47): a book the member has in her Library, or another edition of one, whose title and authors hold every word of the query gets +50, so "dispossessed" finds hers next to the query although unrelated books carry the exact title; a match of title and first-author words ("piranesi clarke") gets +15, above an exact title alone; a summary or study guide of another book (`isSummary`: the words summary, study guide, SparkNotes, CliffsNotes, book review, key takeaways, chapter by chapter in the title) gets −60 unless she has it or the query asks for one. **A result shown without a cover (a Placeholder) also drops 10** (#104, `RANK.coverless`; every neighbouring match tier is within 10), so it never outranks a comparable one that has a cover, and a covered result of the next tier down comes first — while a much worse covered match still ranks below it. Exempt, so they stay on top: exact matches (the title itself, the title without its subtitle, title and author) and the member's own books (the +50 above), cover or not. The adjusted score decides; ties as above.

### Save offline and sync later  (web: `data/queuedWrites.ts`, `data/outbox.ts`, `clearLocalDatabase` in `data/localData.ts`, `WriteOptions.queue` in `data/library.ts` and `data/collections.ts`, `stores/sync.ts`, `rebase`/`applyWrites` in `stores/library.ts`, `readsOf` in `stores/history.ts`, `components/shell/{SyncChip,SyncSheet}.vue` in `components/shell/Header.vue`, `public/sw-sync.js` (`pwa.workbox.importScripts`); database: `sync_write`, `synced_writes`)
Purpose: issue #93. A change made without a connection is no longer refused: it is saved on the device, shown at once, and sent to the database in order once the connection is back. Nothing that waits is shown as synced, and what the database refuses is undone and said.

|---|---|---|

| `start_reading`, `read_again` | wait | entry id; the new read gets a local id until it syncs |
| `finish_reading`, `abandon_reading` | wait | entry id |
| `update_session` (Edit a read) | waits | session id (a local one is rewritten once its start syncs) |
| `remove_from_library` | waits | entry id |

How (data layer):
- The repositories take `{ online, queue }`. While the queue holds (offline, the outbox not read yet, or earlier writes still waiting, so nothing overtakes them) a queueable write is not sent: its arguments, exactly those of the online RPC, go into the outbox with an id made on the device, and the repository answers with the entry as the database will have it (`applyWrite`). What the database would refuse on the device's copy (`not_reading`, `already_reading`, `progress_invalid` …) is refused at once and does not wait.
- The outbox is per member, in IndexedDB (`libellus` database, `outbox` store; `LOCAL_DATABASE`), written whole on every change. Sent oldest first through `sync_write(p_request_id, p_action, p_args)`, which calls the same function as the online path and records the id in the same transaction: a write sent twice (an answer lost) is applied once, answered from the record (`replayed`). Rows a write made come back as `entry_id`/`session_id`; the outbox keeps the device's id → the database's and rewrites every write behind it.
- A send that gets no answer (status 0) or a server error (5xx, 401, 408, 429) stops the line there and is tried again after 2 s, 4 s, 8 s … up to 5 min (`backoff`); a server error 8 times in a row becomes a failure (`unknown`). A refusal (any code the database raised by name) drops that write as a failure (`SyncFailure`: what, about which Book or Collection, the code); the writes behind it are still sent.
- The idempotency record is swept daily: `purge_synced_writes()` deletes the `synced_writes` rows older than 30 days (a write never waits that long), run by a pg_cron job (`purge-synced-writes`, 03:30 UTC) where pg_cron exists; `sync_write` still drops one member's rows older than 60 days as she syncs.
- A connection that answers nothing (#105; `data/network.ts`, `composables/useOnline.ts`): the browser's `online` flag only knows there is no network at all. A write to the REST API (a POST, PATCH or DELETE; not a read, not the auth calls, not `search_books`, `import_books` or `invite_code_status`) is given 8 s to be answered (`WRITE_TIMEOUT_MS`, `withWriteTimeout` in the client's `fetch`) and is cut off after that: supabase-js reports it as status 0 like any network failure (`isNoAnswer`). Such a write is **not an error to show**: a write that can wait goes into the outbox as if the device had known it was offline (`unanswered` in `queued`, in the Library and Collections repositories) and shows the entry as it will be; one that cannot wait (Change edition, Delete a read, a manual book, a new Collection) is refused as `offline`. Either way `useOnline` turns false (`reportNoAnswer`) and every write says "Offline" until the backend answers again: a reachability probe (`createProbe`: `GET /auth/v1/health` with the anon key, 4 s, any answer below 500) is asked after 2 s, 4 s, 8 s … up to 30 s (the pause grows with each write that got no answer and starts over when a write is answered), and the browser's `online` event asks at once. A write that is answered, a refusal included, ends it (`reportAnswer`). The probe also runs before every flush (`reachable` in `createOutbox`): when nothing answers nothing is sent, so no waiting write is held up for a whole timeout, the device counts as offline, and the flush is tried again after the same doubling pause. A write whose answer was lost after the server took it and that then waits is sent again through `sync_write` under a new id; the database refuses what no longer fits (`not_reading` …) and it shows as a failure like any refusal.
- Sent when: the app starts with a connection (once the outbox is read), the `online` event, the app coming back to the foreground (`visibilitychange`), right after a write while online, the retry timer, and the service worker's Background Sync (`libellus-outbox`; where the browser has it, the worker tells the open window to sync; the writes need the member's session, so with no window open they go on the next start).
- After a flush that synced or refused something the Library is read again and the writes still waiting are laid over it (`applyWrites`): a refused write's change disappears (the rollback), a synced one stays; the tally, open histories, the reading days and the Collections are read again. While writes wait, the Collections, memberships and an open history are not refreshed from the database (the device's copy stands). The device's copy of the Library (`libellus.library`) holds the waiting changes too, so a reload offline shows them; it is laid over again once the outbox is read, for a copy saved before a write that waited.
- Signing out deletes the device's IndexedDB database with the waiting writes (a shared phone). So with writes waiting, Sign out (Profile, `profile.signOut`) asks first (`signOutUnsynced`, `UiConfirm` with an `alternative`): "N changes have not synced yet" / "If you sign out now, they are lost." with **Sync first** (online only, `signOutUnsynced.alternative`: sends everything now, pauses or not, and signs out once nothing waits; if something cannot go, `signOutUnsynced.error` says so and she can try again), **Sign out anyway** (`signOutUnsynced.confirm`) and Cancel. Offline only Sign out anyway and Cancel.
States: nothing waiting (no chip) · waiting (chip "Waiting to sync (N)") · syncing (the sheet says "Syncing N changes…") · refused (chip "Couldn't sync (N)" in the error colour once nothing waits; the sheet lists them).

Purpose (#131, phase 1): EPUB files the member has on her device are linked to Books in her Library, from three places: the share sheet (one or many files), the ebook folder (picked once, scanned on a tap) and the file picker on a Book page. Nothing is ever uploaded: every linked file is **copied into the origin private file system** (OPFS), so reading it later (phase 2) needs no permission and works offline; the folder handle only finds files (phase 0, decided by the owner).
Taking a file in (`ingestEbook`, in a worker with fflate): the package document (`META-INF/container.xml` → OPF; its text decoded by its byte order mark, else the encoding its XML declaration names, else strictly as UTF-8 with Windows-1252 for bytes that are not, and composed to NFC, `decodeXml`, so a "u" with a combining diaeresis is "ü") gives the title (EPUB 3's `title-type` main, else the first), the authors (`dc:creator` without editors, translators, illustrators by `opf:role` or EPUB 3's `role` refinement; "Last, First" turned round), language, publisher, every ISBN (`urn:isbn:`, `isbn:`, an identifier labelled ISBN by `opf:scheme` or `identifier-type` 15/02, or a bare valid ISBN-13; ISBN-10 converted) and the cover image (EPUB 3 `cover-image`, EPUB 2 `<meta name="cover">`, else an image item called cover). The copy's name is its fingerprint: SHA-256 of the first megabyte plus the size (`ebooks/<member id>/<hash32>-<size>.epub`, the cover beside it as `.cover`). The same bytes are one copy and one record, whatever they were called or wherever they came from. Not an EPUB → `not_epub`; the copy could not be written → `storage`.
The record (IndexedDB `libellus` → `ebooks`, keyed by member and id): OPFS path and cover path, original name, size, last change (null for a shared file: the share sheet gives the time it was received), the path inside the picked folder, the fingerprint, the metadata, the state (*linked* to a Book and its entry, *unlinked* with its candidate Books, *ignored*), when it was linked and added, and its source (`folder` | `share` | `picker`).
