# Third-party data, services and code

BetterReads is a public repository and talks to services it does not run. This page lists what, why, under
which terms it knows of, and what is kept. It is a plain statement of how the code behaves, not legal
advice; the owner keeps it current when a source is added (the enrichment sources are also in
[ENRICHMENT.md](ENRICHMENT.md), the hosting in [HOSTING.md](HOSTING.md)).

## Data sources

| Source | Used for | How it is reached | Terms, as far as the project knows them | Kept |
| --- | --- | --- | --- | --- |
| Apple Books (iTunes Search API) | Search results, covers, genre names | Browser (search) and the `enrich` edge function | Apple's [Search API terms](https://performance-partners.apple.com/search-api) allow lookups for linking to and promoting Apple content and ask for attribution; the results are not a database to copy. BetterReads stores what a member adds (title, author, cover address), not the catalogue | The Book a member adds; the cover address (`books.cover_url`). The image at our edge (*Cover cache*) and, for a Book in a member's Library, in our own bucket (*Own covers*) |
| Open Library | Search results, covers, fallback metadata | Browser (search, covers), `enrich`, and the `openlibrary` edge function for the **import** (server side, identified and paced: `Libellus/1.0 (<contact>)`, at most 3 requests a second across every instance, one pace booked in Postgres; [supabase/functions/openlibrary/README.md](../supabase/functions/openlibrary/README.md)) | [Open Library](https://openlibrary.org/developers/api) publishes its catalogue records as open data (see its site for the current terms); its published rate limits are 1 request a second for an unidentified client and 3 for an identified one (a `User-Agent` with a contact address; a browser cannot set one, hence the import's asks go through our function and fall back to direct at 1/s when it fails). Covers have their own terms. `books.cover_url` stores the source address; the browser asks for the image through our own edge cache (*Cover cache*), and the server keeps a copy of the cover of a Book in a member's Library (*Own covers*) (the Covers API is "intended for displaying covers on public facing websites and not for bulk download"; by cover id it has no per-address limit, by ISBN 100 requests per IP per 5 minutes; the import's cover fill asks `api/books` for up to 25 ISBNs in one call, one call at a time, and links the cover by its id, [cover-sources.md](plans/cover-sources.md)) | Fields of a Book a member adds; the cover address; the image at our edge (*Cover cache*) and, for a Book in a member's Library, in our own bucket (*Own covers*) |
| Wikidata | Authors, works, series, genres (`enrich`) | `enrich` edge function, server side | CC0 | Facts (names, series, genres) in the database |
| German National Library (DNB, Deutsche Nationalbibliothek) | German editions no other source knows: the barcode scan and the ISBN lookups, the edition picker, the import's match | `dnb-lookup` edge function, server side (SRU, `services.dnb.de/sru/dnb`, identified `User-Agent`); the browser never contacts the DNB | Its catalogue is open data (CC0: no attribution, no storing limit; docs/ENRICHMENT.md). The covers its catalogue shows are licensed to libraries and are never used or stored | The edition's facts (title, authors, ISBN-13, publisher, year, pages) on a Book a member adds or imports |
| Wikipedia and Wikimedia Commons | An author's short intro and portrait (`enrich`) | `enrich` edge function | Wikipedia text is CC BY-SA, a Commons file has its own licence. The app shows the credit (artist, licence, link) the licence asks for, from the stored `credit` ([ENRICHMENT.md](ENRICHMENT.md), "Credits") | The intro, the image address and its credit |
| Goodreads | A Book's community rating, ratings count, reviews count and id | `goodreads-rating` edge function, **server side only**; the browser never contacts Goodreads | Goodreads has no public API for this and its terms forbid automated access to its site. The function reads the endpoints its own site uses, one Book at a time on demand, with a cache (30 days for a hit, 7 for a miss), and keeps only the figures and the id, never review text. This is an **owner-accepted risk**: the feature is optional and can be removed (delete the function and the line on the Book page) if Goodreads objects | Figures and the id, per ISBN or title key |
| Goodreads covers | The cover of a book without one, as a **last resort** (a Goodreads export's rows and a manual "find a cover") | `goodreads-rating` with `cover: true` (the same unofficial `auto_complete` search); the browser then loads the image from `i.gr-assets.com`, and for a Book in a member's Library our own server copies it (*Own covers*) | The address is stored (`books.cover_url`; the answer cache keeps the address next to the rating), no description, page count or rating from this path. Same terms position as the row above. **Owner-accepted risk**, and since **30 October 2026 the image is stored like the other covers** (owner decision): one image, the one the address names, at the size Goodreads serves, copied server side, identified and paced; the app still shows a Goodreads address only while `private.cover_allowed` allows it (`GOODREADS_COVERS` in `web/app/data/coverRank.ts` decides whether this route is used at all; docs/covers.md, *Goodreads, the last resort*). Taken down: drop `goodreads` from `COVER_STORE_HOSTS` (one line, the job stops fetching it) and clear those Books' keys (`update public.books set cover_key = null, cover_widths = null where cover_url like 'https://i.gr-assets.com/%'`), then GC deletes the objects after its 30-day grace; nothing is deleted by hand (docs/OPERATIONS.md, "Own covers"). To stop using Goodreads altogether: the flag set to false and `i.gr-assets.com` dropped from `private.cover_allowed`; those Books show the cloth cover | A cover address per Book; the image of a Book in a member's Library in our bucket (*Own covers*) |
| Hardcover covers | The cover of a book in a Hardcover "everything" zip: the export names an image per book and edition (`cached_image`, always on `assets.hardcover.app`), and the import uses the one of the edition the member has, ranked right after the matched edition's own cover and before any other edition's, Open Library's or Goodreads' | The device puts the address on the row (`coverHint`) and the import job uses it without a request; afterwards the app's own cache (`/cover`, *Cover cache*) and the cover store (*Own covers*) fetch the one image from that one host, server side. **What Hardcover receives: nothing from a member.** No account, no export, no title, ISBN or list ever goes to it; the only requests are for an image's address, made by our server (the stored copy), by our Cloudflare cache (`/cover`), and, when neither can answer (or the instance runs without the cache), by the member's own browser like any image, which then shows its IP address and the image address and no account. There is no Hardcover API call and no token (owner decision, 31 October 2026) | Hardcover publishes no terms for these images; the export hands a member her own data with the addresses, and the images are publishers' covers that members uploaded, the same position as the Goodreads covers. Its API documentation says it makes "no copyright or proprietary rights over this data". **Owner-accepted risk (private app, a few friends, one copy per Book a member holds, server side, paced).** **Owner decision (31 October 2026): these covers are never shown on a public surface.** `private.cover_shown` is false for `assets.hardcover.app`, so a shared reading page, the `/r/` link preview and its image, the feed, a profile and every other answer made for somebody who is not the member carry neither the address nor the stored copy's key and draw the generated cover; they show inside the app only. Taken down: drop `hardcover` from `COVER_STORE_HOSTS` (one line, the job stops fetching it) and clear those Books' keys (`update public.books set cover_key = null, cover_widths = null where cover_url like 'https://assets.hardcover.app/%'`), then GC deletes the objects after its 30-day grace (docs/OPERATIONS.md, "Own covers"); to stop using the source altogether, drop `assets.hardcover.app` from `private.cover_allowed` in a migration (those Books then show the cloth cover, a better source filling in later). A zip's rows carry no hint while `NUXT_PUBLIC_IMPORT_ZIP` is off | The address per Book (`books.cover_url`); the image of a Book in a member's Library in our bucket (*Own covers*) |
| Cover cache (Apple, Open Library, Hardcover) | Faster covers: the sized image of a cover is served from our own address | `web/functions/cover.js`, a Cloudflare Pages Function: `/cover?u=<cover address>&w=<width>`. Only `*.mzstatic.com`, `covers.openlibrary.org` and `assets.hardcover.app` covers on an allowlist, only the sizes those hosts offer (Hardcover's one image as it is; no resizing service); the image is kept in Cloudflare's Cache API for a year (`Cache-Control: public, max-age=31536000, immutable`, refreshed after 30 days), nowhere else: no bucket, no database, no copy in our storage ([HOSTING.md](HOSTING.md), "The cover cache") | The hosts' terms allow linking the artwork (Apple's Search API terms) and displaying covers on public-facing sites (Open Library's Covers API: "not for bulk download"); a cache at our edge is more than a link. **Owner-accepted risk (29 Oct 2026, same position as the Goodreads covers row):** BetterReads is a private app used by its owner and a few friends, not a public service, and draws no benefit from the covers. The images are fetched when a member's device asks for them, never in bulk or ahead of time. Taken down: set `NUXT_PUBLIC_COVER_PROXY=off` (the app asks the hosts directly again) and delete `web/functions/cover.js` (the address then answers the app shell); the service worker's `libellus-cover-cache` is emptied on sign-out | A cover image, at our Cloudflare edge only, for up to a year |
| Own covers (Apple, Open Library, Goodreads, Hardcover and Regal's library) | Fast, dependable covers: the cover of a Book in a member's Library is served from our own address, so it no longer waits on (or depends on) the host being up | `supabase/functions/cover-store`, an edge function that writes, and `web/functions/c/[[path]].js`, a Pages Function that serves `/c/<key>/<width>`. Server side only: identified (`Libellus/1.0 (<contact>)`), paced (Open Library's keyed covers at 0.3 requests a second), the sizes the host itself renders (Apple's 120, 240, 360 and 600 boxes, Open Library's `-L` and `-M`, one image for Goodreads, Hardcover and Regal), one copy per image, and only once a member holds the Book, never ahead of that and never in bulk. The key is an HMAC of the image with a secret, so it cannot be derived from a cover and says nothing about a member; the copies sit in the private R2 bucket `libellus-covers` (no public access, no `r2.dev` address, no custom domain) and leave it only through our own `/c/` ([HOSTING.md](HOSTING.md), "Own covers") | Apple's Search API terms allow the artwork for linking to and promoting Apple content; Open Library's Covers API asks covers to be shown on public-facing sites and not bulk-downloaded; Goodreads' terms allow no automated access at all (the row above). A stored copy is more than a link, hence the **owner-accepted risk (30 October 2026, the same position as the *Cover cache* row):** BetterReads is a private app used by its owner and a few friends, not a public service, and draws no benefit from the covers; the copies are made only of books a member holds, one per image, server side and paced. Taken down: set `private.cover_store_settings.enabled = false` (nothing more is stored and the copies stay served), or drop a host from `COVER_STORE_HOSTS` and clear its Books' `cover_key`; a stored image is deleted 30 days after no member's Library holds its Book, and a deletion is irreversible (docs/OPERATIONS.md, "Own covers"). The function's log carries Book ids and error kinds, never titles, ISBNs or cover addresses | A cover image per Book in a member's Library, at a few widths, in the private bucket, until 30 days after no Library holds the Book |
| MyMemory (Translate) and Wiktionary (Define) | The built-in reader's "Translate" and "Define" on selected words | Browser, only with the words a member selected | MyMemory's and Wiktionary's own terms (Wiktionary: CC BY-SA) | Nothing |
| Goodreads and Hardcover exports | A member's own history | A Goodreads CSV, a Hardcover CSV or the Hardcover "everything" zip, which the member chooses; parsed in the browser (a zip is opened on the device and only the files the import needs are read: the library, reads, editions, lists and cover addresses; the rest is never decompressed) | The member's own data | What the member imports |

## Services that process data

The ones that store or process members' data (Supabase, Cloudflare Pages, Cloudflare R2, Resend, Sentry) are listed with
what each holds in the [README](../README.md) ("Where your data lives"). GitHub holds the code and
its CI only. Sentry (Functional Software, Inc.; error reports and performance measurements, EU region Frankfurt, only when a DSN is set, kept 30 days) gets no account id, name, email, IP address or content: what it receives is in README "Sentry" and the privacy notice.

## Test fixtures: test-only recordings

The recordings under `web/tests/fixtures/` (`apple`, `openlibrary`, `goodreads`, `hardcover`, `barcode`, `ebooks`) and
`supabase/functions/*/fixtures/` are answers of those services recorded for the tests (so no test reaches a
real host) and are **for testing only**. They stay in the repository so a clone can run the suite offline. They are not
part of the app, are not served, and are not licensed for any other use: the data in them belongs to the
services above under their own terms. Do not build on them and do not add real members' data to a fixture.
